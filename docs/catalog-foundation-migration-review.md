## Approved rules and implementation choices

- One workbook row is one sellable Product; UUID primary IDs remain independent of names, categories and immutable system-issued SKUs.
- UUIDs use Prisma `uuid()` (generated by Prisma, not a SQL column default). Direct SQL would need to provide UUIDs. Physical table/model names use PascalCase and camelCase columns, matching existing Prisma conventions without unnecessary mappings.
- ProductPublicationStatus is exactly DRAFT, PUBLISHED, ARCHIVED; DRAFT default. Availability is independent and defaults false as a conservative implementation choice. No schema rule forces published products to be available. Publication readiness checks remain a future business/API decision.
- Editable sellingUnitLabel defaults `piece`. Future import review flags sets/packages/sheets; no automatic physical quantity conversion. minimumOrderQuantity defaults 1 for new manual products, but importer must explicitly use source quantities (25 for current workbook). No records were imported.
- Catalog prices/costs are Decimal(18,4), nonnegative, finite and bounded by that type. Cost is optional; costBasis must be non-null when cost exists. An absent cost can retain a classification without implying an actual amount; this avoids adding an unapproved inverse requirement.
- Small provenance enum: `REVERSE_CALCULATED_ESTIMATE` for this workbook's illustrative reverse-calculated costs; `MANUAL_ESTIMATE` for an explicitly entered planning estimate. Neither means verified actual acquisition cost. Unknown cost is null, not invented zero. No automatic recomputation when unitPrice changes. New provenance values require later explicit review.
- specificationText is nullable Text; preserve supplied source wording verbatim. No dimensions, variant, image or file model is required. Attribute text is optional at product level, with unique keys per product.
- Timestamps are timestamptz(3), UUIDs are UUID, descriptions/attributes are Text. createdAt defaults now; updatedAt is Prisma-managed `@updatedAt` (no automatic SQL update timestamp trigger). Direct SQL must provide updatedAt on creation and maintain it on edits. Product version defaults 1 and is positive, but optimistic increment/compare is a future API responsibility.

## Sequence and trigger design

`public.product_sku_sequence` is a bigint sequence starting at 1, incrementing by 1, NO CYCLE. The Product BEFORE INSERT trigger rejects any non-null caller SKU, then calls nextval once. Prisma `@default(dbgenerated())` marks SKU as optional on create; it intentionally emits no SQL DEFAULT, because the trigger fills the omitted value before NOT NULL validation. Generated create/update types still technically expose sku: future API allowlists must omit it; DB triggers provide enforcement even if an application accidentally sends it.

Formatting uses `T29-P-` plus `lpad(numberText, greatest(6,length(numberText)), '0')`. Examples: 1 → T29-P-000001; 999999 → T29-P-999999; 1000000 → T29-P-1000000. Width expands rather than truncates beyond six digits. Exhaustion at bigint maximum fails; it does not wrap/reuse. Product names/categories never participate. A BEFORE UPDATE trigger rejects changes while allowing a no-op assignment to the same SKU.

PostgreSQL documents atomic nextval allocation and non-rollback of allocated values: [sequence functions](https://www.postgresql.org/docs/18/functions-sequence.html). Concurrent callers obtain distinct numbers. Failed inserts, transaction rollbacks, ON CONFLICT attempts and crashes can leave gaps. Do not promise numerical order equals commit order; publish a SKU externally only after commit. Deleting/archiving a product does not rewind the sequence. Manual reseeding, sequence restart, trigger bypass and schema reset are prohibited routine operations.

Triggers run SECURITY INVOKER with a fixed pg_catalog search_path and schema-qualified sequence references. On later application, migration ownership/privileges must be reviewed: routine API DML identity needs only sequence USAGE, not UPDATE (setval), and must not own/alter tables/functions/sequence or disable triggers. No grants or role alterations are included now. An owner/superuser can intentionally bypass these safeguards; application-level immutability alone is insufficient, while database triggers plus restricted role privileges protect the routine write path. Restore procedures must preserve sequence high-water marks and not reuse issued identifiers; gapless issuance is not a goal. These are review requirements, not claims that the current project's object ownership was changed.

## Catalog precision versus financial rounding

The approved future posted PHP total is Decimal(18,2) with explicit half-up rounding. This task implements no financial posting, rounding, taxes or discount calculations.

PostgreSQL coerces a numeric value to the declared scale before a stored-row CHECK can inspect it; [numeric type behavior](https://www.postgresql.org/docs/18/datatype-numeric.html). Therefore numeric(18,4) plus CHECK cannot reject an originally supplied fifth fractional digit after coercion. The draft does not falsely claim that protection. Before any future catalog write/import is enabled, validate decimal-string precision and range before Prisma/SQL assignment, reject excess precision, avoid binary floating point, and test boundary values. No public/business write path exists in this task. Direct ad-hoc writes are not an approved bypass. If every arbitrary SQL client must reject rather than coerce excess precision, a separately reviewed write boundary/type design is needed; do not silently change the approved Decimal(18,4) columns to achieve that here.

## Offline preparation and verification boundary

Used installed Prisma 7.10.1 tooling:

```text
node node_modules/prisma/build/index.js format --config apps/api/prisma.config.ts
node node_modules/prisma/build/index.js validate --config apps/api/prisma.config.ts
npm.cmd run db:generate
node node_modules/prisma/build/index.js migrate diff --config apps/api/prisma.config.ts --from-empty --to-schema apps/api/prisma/schema.prisma --script --output .tools/phase3a-generated-base.sql
```

The diff compares an explicitly empty datamodel to a local schema file. No datasource/shadow/introspection flags, migrate dev/deploy/reset, db push or db execute were used. Existing Prisma config may load the ignored .env locally but validation, generation and this datamodel-only diff do not query the live database. Schema-driven SQL was generated, then hand-authored CHECKs, sequence and trigger definitions added under a BEGIN/COMMIT transaction. Do not run plain generated base SQL: it lacks the required hand-authored safeguards.

Prisma validation validates the Prisma model language, not hand-authored SQL or live trigger behavior. Generated client types and API build/lint/existing mocked tests are separate checks recorded in status/report. SQL was reviewed offline against schema and documented invariants; no PostgreSQL parse/apply test or concurrent-session execution was performed. Trigger-created value RETURNING behavior with the driver adapter, rejection checks, SKU immutability and real race tests require a separately authorized temporary database/migration milestone. No temporary DB was created.

Custom triggers, sequence ownership and CHECKs are not fully represented by Prisma's datamodel diff. Preserve/review custom migration SQL, never blindly regenerate it from schema or use db push. Future introspection may remove no-expression dbgenerated metadata; preserve the intended trigger contract explicitly. An empty-to-schema diff is a preparation baseline, not proof the live database is empty or free of name conflicts.
