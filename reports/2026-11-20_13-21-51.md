# Phase 1A catalog database verification

Started 2026-11-20_13-21-51 Asia/Manila (UTC+08:00).

Verifying live catalog status and isolated migration behavior.

## Task overview

Verify the existing catalog foundation for Phase 1A and review live database ownership prior to catalog writes. Preserve the original SQL and require separate authorization for live provisioning and application.

## Work completed and technical findings

- Inspected the Prisma schema, migration, API configuration/provider, catalog design, and existing tests. Category, Product and ProductAttribute are defined with UUID IDs, restrictive parent relations, and unique catalog identifiers. Product has independent publication and availability, Decimal(18,4) amounts, and trigger-issued SKUs. The API exposes health endpoints only. There is no catalog CRUD or Admin product management.
- Ran read-only PostgreSQL queries before and after disposable testing. The configured local PostgreSQL 18.6 database has no public relations, enums or functions and no Prisma ledger. Both configured URLs resolve to the same connection configuration. The migration is unapplied on this target.
- The shared login has no superuser, create-role, create-database, replication or bypass-RLS flags. It has database and public-schema ownership rights and CREATE privileges. Using it as the runtime identity would let the API own and alter catalog objects if it ran the migration.
- On a separately initialized loopback PostgreSQL 18.6 cluster, a non-superuser database owner ran the original migration successfully. A separate login could create categories and update catalog rows with public schema USAGE and table SELECT, INSERT and UPDATE. Product creation required sequence USAGE. The runtime login was denied setval, trigger changes, schema CREATE and migration ledger reads.
- The database rounds excess scale before CHECK constraints run. Follow-up API writes must validate decimal strings for scale and range before assignment. Prisma introspection drops the trigger-backed SKU default annotation. Preserve the checked-in model and hand-authored SQL when reviewing future migrations.

## Issues and attempted failures

- Windows pg_ctl start failed to create a restricted token (error 87). Starting postgres.exe directly worked.
- Initial Angular builds and tests failed because the sandbox denied ancestor-directory traversal. An access-approved rerun passed.
- The disposable harness needed corrections. An invalid estimate initially tripped the provenance CHECK first, so the nonnegative tests were given valid provenance. Two subsequent attempts caught an extra CREATE ROLE under the migrator and a SQL identifier interpolation mistake. PostgreSQL 18.6 returned SQLSTATE 23001 for parent RESTRICT violations, so the check was corrected from 23503. The complete corrected run passed against a fresh disposable database. These failures did not require migration changes.
