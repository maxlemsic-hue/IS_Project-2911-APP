# POS Phase 1 — Walk-in ordering

Implementation and disposable verification completed. Regular local activation awaits migration approval.

## Task outcome

Implemented the Angular cashier interface and a staff-protected walk-in creation endpoint using the existing NestJS ordering service. The full workflow passed on disposable PostgreSQL and in Edge. The regular local database retains nine applied migrations. Approval was requested for the tested additive migration 20261120235245_pos_walk_in and has not been received as of this report.

## Features implemented

- Individual staff login/logout and session restoration through the existing staff authentication.
- Cashier and Owner/Admin access. Production Staff sees a restricted screen.
- Real catalog products, images, SKU/name search, category filtering and current prices.
- Multi-product cart, quantity editing, minimum/range validation, removal, exact 0.0001 PHP estimates and required customer name/contact fields.
- Success screen with one reference, saved snapshot items, total and the existing private customer code for handoff. Cart clears after success; request failures retain selections.
- Responsive cream, green and coral POS layout for desktop and tablet.
- Pending Review walk-in creation using the same catalog eligibility, customer validation, line validation, server prices and transaction as online ordering.
- WALK_IN order source, creating staff foreign key and WALK_IN_CREATED staff audit event committed with the order.
- A POS link in the existing Cashier-restricted Admin screen.

POS creation does not bypass the existing order lifecycle. Owner review, customer confirmation, manual payment verification, minimum deposit, manual stock check and full-payment release conditions remain enforced. Payment collection and inventory are deferred.

## Database changes and safety

Prepared 20261120235245_pos_walk_in, SHA256 dae6beb868d0df9ca1ddcaa0f872eb3d21ef7a5a11c6a9af1f35b8cedf6f309d. It adds OrderSource (ONLINE/WALK_IN), a native ONLINE default, nullable createdById with restrictive StaffUser FK, an index, a creator-required check for WALK_IN and the creation audit action. Existing orders become ONLINE with no creator.

The database-owned enum default is represented with Prisma dbgenerated and a text-to-enum expression. This avoids application-side insertion of a new source column for legacy online submissions before activation. The tested database schema diff is empty, and online creation/retrieval worked before and after the disposable upgrade.

Verified the regular non-production loopback PostgreSQL target, matching runtime/direct URLs, existing nine successful migration checksums and POS CORS origin. Created .tools/mvp-pre-migration-1795189965636.dump (75,085 bytes). Archive listing and full pg_restore decode passed. A restore was not performed. The backup and local fixture credentials/logs are Git-ignored.

Only disposable PostgreSQL received the new migration. No real migration, reset, deletion, database-role change or application test writes were made to the regular database.

## API

POST /api/v1/pos/orders requires an authenticated Cashier or Owner/Admin and the existing X-Staff-Request header. It accepts the same multi-item payload and required customer fields as online ordering. Client prices, source, creator and status claims do not control saved values. Server-owned source/creator and audit attribution are used.

The existing online endpoint and private order/customer workflow retain their response contracts. Admin sees walk-in orders in the existing queue and can inspect the creating Cashier in staff actions.

## Issues found and resolved

Initial disposable online submission exposed Prisma's application-owned enum default attempting to write the new column before migration. Changed source assignment to a compatible native database default. Intermediate default representations produced schema-diff output; the final expression round-tripped without drift. All of these checks used disposable databases.

A money test initially contained an incorrect expected sum. Corrected it to PHP 659.8752 for 17 units at PHP 12.3456 plus 25 units at PHP 18. The arithmetic implementation was correct. POS styles initially exceeded the warning budget by 23 bytes; removed redundant margins. Browser tooling needed separate add-to-cart interactions to let the existing storefront state render between events. Final checks passed.

A broad formatting check noticed the untouched POS routes file. Left it unchanged and verified only task-modified files.

## How to operate after approved activation

Start PostgreSQL and run npm.cmd run dev from the root. Open http://localhost:4201. Owner/Admin creates an individual Cashier account through the existing Admin Staff accounts interface, if needed.

Sign in, find products, add items, adjust whole-number quantities and enter customer name/contact. Submit the walk-in request. Save and give the customer the reference/private code. Admin reviews the order at http://localhost:4200/orders. The customer uses http://localhost:3000/#tracking for the existing confirmation and communication workflow.

The regular database requires the pending migration before new walk-in orders can be submitted. The tests in this report used the isolated API/database through browser request forwarding. Disposable staff credentials were generated in memory and were not exposed or written to reports.
